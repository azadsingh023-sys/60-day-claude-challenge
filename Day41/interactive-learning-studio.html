MODULE 1 / 4 · FOUNDATIONS

What makes a script "automation"?

Before writing any code, you need the mental model: an automation script is a small, unattended program built around a trigger, a job, and an outcome — not just "a Python file that does something."

The trigger → job → outcome model

Every automation has three parts: something that starts it (a trigger — you running it, a schedule, a new file appearing), the work it performs (the job), and the change it leaves behind (the outcome — a file moved, an email sent, a report generated). Ordinary scripts you write while learning Python usually skip the "trigger" question entirely, because you're the trigger — you hit run. A real automation has to work when you're not watching it run.

🏭
Analogy — the vending machine, not the chef. A chef (a normal script) needs you present to decide each step. A vending machine (an automation) is stocked once, then reacts the same correct way every time someone presses a button — including at 3am when nobody's there to fix a mistake. Automation scripts are designed for the 3am case.

Two example scripts, same task, different mindsets

Not automation-minded — assumes a human is watching
files = os.listdir("downloads") for f in files: print(f) # human reads this and moves files by hand
Automation-minded — the script does the moving itself, and won't crash the whole batch on one bad file
import shutil, os for name in os.listdir("downloads"): ext = name.split(".")[-1].lower() dest = os.path.join("downloads", ext) try: os.makedirs(dest, exist_ok=True) shutil.move(os.path.join("downloads", name), dest) except Exception as e: print(f"Skipped {name}: {e}") # keeps going instead of dying

Common misconceptions

✕"Automation" means using a special automation library.
No special framework is required — os, shutil, and the standard library are enough for most everyday automation. It's a design mindset (unattended, resilient) more than a toolset.
✕If it works once when I run it, it's done.
Working once on your machine, with your files, tells you nothing about next Tuesday when a folder is empty or a filename has a space in it. Automation scripts are judged by how they behave on inputs you didn't test.

Key takeaways

  • Automation = trigger + job + outcome, designed to run without you watching.
  • The defining trait isn't cleverness — it's resilience to unattended failure.
  • Standard-library modules (os, shutil, sys) already cover most automation building blocks.
MODULE 2 / 4 · FILES & DATA

Files, folders, and structured data

Most automation is really data movement: reading something in one shape, and writing it back out in another. This module covers the file-system toolkit and the two data formats you'll meet constantly — CSV and JSON.

pathlib vs os.path

Modern Python favors pathlib.Path for file paths — it treats a path as an object with methods, rather than a string you glue together. Both work; pathlib reads more clearly in new scripts.

from pathlib import Path folder = Path("reports") for file in folder.glob("*.csv"): print(file.name, file.stat().st_size) # same idea with os.path (older style) import os for name in os.listdir("reports"): if name.endswith(".csv"): print(name)
🗂️
Analogy — a filing cabinet vs. loose string labels. os.path is like labeling folders with pieces of string you tie together ("reports" + "/" + name) — it works but is fragile. pathlib gives every folder a proper handle with built-in actions (.glob(), .exists(), .stat()) — a filing cabinet where every drawer already knows how to open itself.

Reading and writing CSV

CSV is the lingua franca of spreadsheets. Python's built-in csv module reads rows as lists or, more usefully, as dictionaries keyed by header.

import csv with open("sales.csv", newline="") as f: reader = csv.DictReader(f) total = 0 for row in reader: total += float(row["amount"]) print(f"Total: {total:.2f}")

Reading and writing JSON

JSON maps directly onto Python dicts and lists, which is why it's the default format for config files and API responses.

import json with open("config.json") as f: config = json.load(f) config["last_run"] = "2026-09-04" with open("config.json", "w") as f: json.dump(config, f, indent=2)

Common misconceptions

✕You must load an entire CSV into memory to process it.
csv.DictReader streams row by row, so even multi-gigabyte files can be processed with modest memory — you rarely need to load everything at once.
✕Forgetting to close a file causes it to lose data immediately.
The real risk is that writes may sit buffered and never reach disk if the program crashes before closing. Using with open(...) as f: closes the file automatically, even on error — always prefer it over manual open()/close().

Key takeaways

  • pathlib.Path is the modern way to work with files and folders.
  • csv.DictReader/DictWriter read/write rows as dictionaries keyed by header.
  • json.load/dump convert directly between JSON and Python dicts/lists.
  • Always use with open(...) as f: so files close automatically.
MODULE 3 / 4 · REAL-WORLD AUTOMATION

Talking to the outside world

Real automations rarely stay confined to your hard drive — they fetch web pages, call APIs, send notifications, and run on a schedule. This module covers the three most common "reach outside the script" tasks.

Calling a web API with requests

requests is the standard third-party library (install with pip install requests) for making HTTP calls — the same mechanism your browser uses, but scriptable.

import requests resp = requests.get("https://api.example.com/status", timeout=10) resp.raise_for_status() # raises an error on 4xx/5xx instead of silently continuing data = resp.json() print(data["status"])
Always set a timeout. Without timeout=, a hung server can freeze your script forever — a common reason "working" automations silently stop running.

Sending notifications

The standard library's smtplib can send email directly; many teams instead post to a webhook (Slack, Discord, Teams) with a simple requests.post() call, which is often simpler than managing email credentials.

import requests requests.post( webhook_url, json={"text": f"Automation finished: {rows_processed} rows processed."} )

Scheduling: inside Python vs. the OS

You can schedule work in two places. A library like schedule keeps a script running continuously and fires jobs at set times — good for long-lived services. For most automation, though, it's simpler and more robust to let the operating system start a short-lived script at the right time: cron on Linux/macOS, Task Scheduler on Windows.

# cron: run every day at 6:30am 30 6 * * * /usr/bin/python3 /home/user/cleanup.py >> /home/user/cleanup.log 2>&1

In-script scheduler vs. OS scheduler

Traitschedule librarycron / Task Scheduler
Process lifetimeMust stay running continuouslyStarts fresh each run, then exits
Survives rebootNo, unless you also manage thatYes — the OS restarts it for you
Good forLong-lived services, dev/testingPeriodic scripts — the common case
⏰
Analogy — an alarm clock you carry vs. one bolted to the wall. A schedule-based script is an alarm clock you have to keep charged and awake yourself. Cron is bolted to the wall (the OS) — it rings on time whether or not your own process is even alive.

Common misconceptions

✕Python has web-request support built in, so you never need to install anything.
The standard library has the lower-level urllib, but requests (a third-party package) is the de facto standard because it's far more ergonomic. It's an install, not a built-in — worth the pip install.
✕Cron and a Python schedule loop are interchangeable — pick whichever.
They behave very differently on reboot and crash. A schedule loop dies with its process and stays dead until someone restarts it; cron re-invokes the script fresh from the OS, which is far more resilient for unattended automation.

Key takeaways

  • requests is the standard tool for HTTP calls — always set a timeout.
  • Webhooks are often simpler than email for automation notifications.
  • Prefer OS-level scheduling (cron / Task Scheduler) over an always-running Python loop for periodic jobs.
MODULE 4 / 4 · MASTERY & RESILIENCE

Making scripts survive the real world

The final skill separating a fragile script from production automation: handling errors, logging what happened, and designing so re-running the script never causes damage.

Structured error handling

Catch specific exceptions, not everything blindly. A bare except: hides bugs; a targeted except FileNotFoundError: lets you respond appropriately and still surfaces truly unexpected errors.

try: with open("input.csv") as f: process(f) except FileNotFoundError: logging.error("input.csv missing — skipping this run") except PermissionError: logging.error("No permission to read input.csv") except Exception as e: logging.exception(f"Unexpected error: {e}") raise # re-raise unknowns rather than silently swallowing them

Logging instead of print()

The logging module gives you timestamps, severity levels, and the ability to write to a file — essential once a script runs unattended, since nobody is watching a console at 3am.

import logging logging.basicConfig( filename="automation.log", level=logging.INFO, format="%(asctime)s %(levelname)s %(message)s" ) logging.info("Run started") logging.warning("3 rows skipped due to bad data")

Idempotency: safe to re-run

An idempotent script produces the same end state no matter how many times it runs — critical because cron jobs sometimes run twice, or you re-run manually after a crash. If your script appends a line to a file every run without checking, running it twice duplicates data.

💡
Analogy — a light switch, not a light-adding machine. Flipping a light switch "on" twice leaves the room exactly as bright as flipping it once — that's idempotent. A machine that adds one more lightbulb every time you press the button is not; press it by accident and you get a room full of bulbs. Design automation like the switch.

Retries with backoff

Transient failures (a flaky network, a server under load) often succeed on a second attempt. Retrying immediately can make things worse; waiting longer between each attempt ("backoff") gives the problem time to clear.

import time for attempt in range(3): try: resp = requests.get(url, timeout=10) resp.raise_for_status() break except requests.RequestException: wait = 2 ** attempt # 1s, 2s, 4s logging.warning(f"Attempt {attempt+1} failed, retrying in {wait}s") time.sleep(wait)

Common misconceptions

✕Catching every exception with a bare except: makes a script "safe."
It makes failures invisible instead of safe — the script keeps running in a broken state and you find out much later, if ever. Catch specific, expected exceptions and let unexpected ones surface (log and re-raise).
✕Retrying immediately in a tight loop is just as good as backoff.
Hammering a struggling server with instant retries can make the underlying problem worse (and can get your script rate-limited or blocked). Exponential backoff gives the system time to recover.

Key takeaways

  • Catch specific exceptions; let truly unexpected ones surface via logging + re-raise.
  • Use logging, not print(), for anything that runs unattended.
  • Design scripts to be idempotent — safe to re-run without duplicating work.
  • Use retries with exponential backoff for transient network failures.
